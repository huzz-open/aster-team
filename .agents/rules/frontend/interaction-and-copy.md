# Interaction, state, and copy

- When an action is disabled because a prerequisite is missing, explain the reason in a tooltip anchored to that action on hover and keyboard focus. A disabled native button may need a focusable wrapper to receive those interactions.
- Do not add a page banner, notice, or paragraph solely to explain why one action is disabled. Use a page-level message when the entire page or flow is blocked.
- Show current state and the data needed to choose the next action in the existing status or detail area. Keep error details reachable without replacing a useful status with a permanent generic loading label.
- Before adding visible wording, identify the user action or decision it supports and the established place for it on that page. If neither exists, omit it. Do not surface an API field as a toolbar caption, status summary, helper sentence, or new text area merely because the field is available. Include any proposed new wording in the visual self-review before coding.
- User-facing interfaces and generated UI mockups must not narrate the implementation to developers. Do not add text that says what the system has already done for the user, why a technical requirement was followed, how hidden mechanics work, or that an implementation matches a request. Before coding or generating a UI image, require every visible sentence to support a user action, decision, current state, or recoverable error; otherwise omit it. Apply the same test to actions: do not invent confirmation or completion buttons when closing the surface is sufficient and no product state transition requires acknowledgement.
- Write concise labels and state descriptions. Avoid persistent explanations of internal processing, duplicated descriptions of controls, or speculative guarantees. Put operational details in documentation or contextual help where needed.
- Use the surface's existing localization pattern for new labels, status text, help, and errors. Preserve accessible names for icon-only actions and keyboard access to contextual guidance.
- Render user-facing enum values such as provider, access method, billing mode, and status as the established compact badge or status component with a localized label. Do not expose raw enum strings as plain table text. Keep identifiers and free-form names as text.
- Match each action icon to the action's meaning: Edit uses the edit icon, credential actions use the key icon only when they specifically manage a key, and verification is distinct from synchronization. When several icon-only actions would be hard to distinguish, use short visible button labels. Do not use a key icon as a generic Edit action.
