# Components and layout

- Search `packages/ui` and comparable views before introducing a control or layout. Prefer shared `A*` components and existing page classes such as `.page-head`, `.card`, `.section-head`, `.tabs`, `.tab`, `.filter-bar`, and `.status` where they fit. Extend a shared component when its behavior is needed by more than one page.
- Use the shared `AFilePicker` for file selection and drag-and-drop uploads. Keep the picker and submit action in the shared `.file-upload-row` layout. Do not expose a raw browser file input in place of the established upload control.
- Use the shared `ASelect` for every user-facing dropdown in Customer, Operations, and Website frontends. Do not render a native `<select>` in product UI. Supply explicit `{ value, label }` options, preserve the control's accessible label, and let `ASelect` enable search automatically for long option lists unless the workflow requires search at all sizes.
- Keep data and actions in the page section where users expect to manage them. Before moving a capability into a menu or tab, inspect the existing sidebar grouping and tab style. Avoid a new standalone card, banner, or entry when an existing area can carry the information.
- When a page manages versions or items of one kind, start from the existing list or table pattern and put item-specific actions in its action column. Use separate sections only for distinct workflows that cannot fit the list and its toolbar.
- Keep one data field per table column. Do not deliberately stack multiple fields (such as a name and description, or an ID and timestamp) on separate lines inside one cell to reduce the column count. Give them distinct columns or put secondary details in the existing detail view. Keep each field on one line in the table, truncate long values with access to the full value on hover, and use the existing horizontal table scrolling on narrow screens. Natural wrapping of a single value outside tables is unaffected.
- When a record's fields fit a normal table row, show them as columns. Do not create an expandable information panel for one record merely to avoid using the table width. If categories have genuinely different fields, keep their rows in the same inventory area and use category-specific table columns rather than duplicating values in a second panel.
- In an entity inventory, use one row per entity. Put its historical revisions or versions in the established detail modal or drawer instead of repeating the entity as multiple main-list rows. Keep version and content digest separate when multiple builds share the same version label.
- Keep the action column visible for a stable per-row operation, even when every current row lacks its prerequisite. Show its disabled control in each row and explain the missing prerequisite on hover or keyboard focus. Omit an action column only when that list has no per-row operation.
- Preserve existing spacing and alignment. Use the current responsive layout pattern for stacked controls instead of fixing a desktop-only composition with one-off widths or offsets.
