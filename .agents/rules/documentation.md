# Documentation maintenance

- Start with [the document index](../../docs/README.md) and read only the topic needed for the task. Keep workflow rules in `AGENTS.md` and implementation rules in this directory; do not duplicate them in plans or READMEs.
- Give each fact one owner: installation/troubleshooting in `docs/user-manual.md`, operator procedures in `docs/operations-guide.md`, public API/command reference in `website/docs`, schemas and catalogs in `contracts`. Link to the owner instead of maintaining a second tutorial or field table.
- Keep rules short, actionable and scoped by a read trigger. Do not promote proposed capabilities, temporary task permissions, historical test results, prices or external-provider experiments into rules.
- A plan must distinguish decisions, implemented code, remaining work and acceptance conditions. Once implemented, move enduring constraints into the relevant rules/reference, then remove the superseded plan. Preserve unresolved requirements and security findings explicitly.
- Record per-run logs, local paths, screenshots and test counts in PR/run artifacts, not accumulating implementation diaries. Historical passes never certify another commit or release. Recover old designs from Git rather than maintaining an archive tree in the working checkout.
- Public Markdown lives in `website/docs` with paired Chinese/English pages. Changes to public CLI commands must update both languages and `website/docs/.vitepress/cli-navigation.ts`; the installation manual remains canonical. Website task guides include its named regions; review paired English summaries when their source changes, following the publishing guide. Hidden maintenance commands stay internal.
- Keep public output allowlisted: never expose `docs/internal`, credentials, private hostnames, signing material or research as published capability. A built page or model list is not proof that its advertised behavior works.
- Use the public [documentation index](../../docs/README.md) for official-site and member-site indexing. Keep pending capability-generation work separate from instructions for the existing site.
- Before deleting or moving a document/asset, check Markdown links, bare paths, build/export allowlists, tests and skill references. Update surviving references and the index together; an unreferenced asset can still be an externally used brand asset.
- Run `npm run verify:docs` for documentation contracts and `git diff --check` for whitespace. PR readiness still requires the exact-head integration workflow in `AGENTS.md`; do not change verification policy merely to simplify documentation cleanup.
