# Aster Team 成员额度与用量结算如何工作

[English](../../guides/quota-reservation-and-usage-accounting.md) · [部署指南](README.md) · [成员指南](../member-guide.md)

Aster Team 为成员独立分配额度，并通过预占与结算处理每次模型请求。这可以防止并发请求同时消费同一份可用余额，同时把用量归属到实际发起请求的成员 API Key。

## 额度生命周期

```text
成员获得额度
    │
    ▼
可用额度 ── 接受请求 ──► 预占额度
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
        获得可信用量                请求未执行
              │                         │
              ▼                         ▼
          完成结算                   释放预占
```

1. 管理员向成员发放额度。
2. 路由请求前，Control 从该成员可用额度中预占在途请求所需容量。
3. 没有符合条件的 Runner 或账号接收请求时，系统释放预占且不扣费。
4. 执行完成后，Aster 按执行路径返回的可信 Usage 结算。
5. 用量记录和额度账本保留成员、Key、模型、协议、请求标识与结算结果，供后续检查。

## 发放、预占、消耗和可用

- **已发放**：管理员、已批准申请或受支持兑换流程增加的额度。
- **已预占**：请求正在执行或等待恢复时暂不可用的额度。
- **已消耗**：已经成功写入账本的实际用量。
- **可用**：扣除已消耗和当前预占后仍可使用的余额。

由于预占用于保护并发请求，页面显示的可用余额可能暂时低于“已发放减去已消耗”。

## 请求中断后的处理

执行后 Control 重启时，会先尝试恢复已持久化的结果并结算原请求。没有可恢复结果的预占会在 30 分钟后进入定期核对。Aster 会释放到期预占，不会猜测 Token 用量，并记录最终上游执行结果不确定。

不要删除结算状态或直接编辑数据库释放额度。超过核对窗口仍未恢复时，请保留 Request ID，并使用 `aster-team-cli trace` 收集 Control 日志。

## 排查额度问题

- `34001 INSUFFICIENT_QUOTA` 表示扣除在途预占后可用额度不足。
- 在管理端或成员端检查发放、已消耗用量和在途预占。
- 确认客户端使用的是正确成员 Key，而不是从其他人员或自动化任务复制的 Key。
- 使用 `X-Aster-Request-ID` 关联 API 错误、用量记录和 Control Trace。
- 增加额度前先确认请求模式和所选模型是否符合预期。

Prompt 和响应正文不会作为业务用量账本。Runner 和基础设施运维人员仍需配置自己的日志访问与保留策略。
