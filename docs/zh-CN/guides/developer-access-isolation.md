# Aster 如何隔离开发者访问、额度与用量

[English](../../guides/developer-access-isolation.md) · [开发者指南](README.md) · [架构](../architecture.md)

Aster 在网关身份与治理层隔离开发者访问。它的目标是不向团队分发上游凭据，同时为每位人员或自动化身份提供可单独撤销的访问路径。

## 隔离层次

| 层次 | Aster 的行为 | 客户责任 |
| --- | --- | --- |
| 身份与 Key | 每位成员或自动化身份获得独立的 Aster API Key | 不跨人员复用；Key 泄露后及时轮换或撤销 |
| 额度 | 按完成认证的成员判断发放额度、预留和可用余额 | 制定分配策略并监控异常用量 |
| 用量与审计 | 请求归属到对应成员路径，并生成运行记录 | 制定用量记录与日志的保留和访问策略 |
| 上游凭据 | 成员无需获得已连接账号凭据 | 限制 Control 与 Runner 管理权限，保护备份 |
| Codex 本地状态 | 可通过不同设备、操作系统用户或 `CODEX_HOME` 隔离 | 需要历史隔离时不要共享同一本地 Profile |
| Prompt 与响应正文 | Aster 业务数据库不用于归档 Prompt/响应正文 | Runner 运维人员能够查看所处理流量，应正确保护主机和日志 |

## 仍然存在的边界

- 第三方服务会在客户已授权账号下处理请求。
- 能够管理 Runner 主机的人员可以查看该主机处理的 Prompt 与响应。
- 两个客户端共享操作系统账号、进程环境和 `CODEX_HOME` 时，不具备可靠的本地历史隔离。
- 客户的 DNS、TLS、代理、可观测系统和主机日志可能根据配置包含运行信息或请求数据。
- Aster 的隔离不会创建独立的上游身份、订阅、积分或合同权益。

## 推荐控制措施

1. 为每个需要归责的人员或自动化任务创建独立身份。
2. 为每个身份分配独立 API Key 和额度。
3. 需要隔离本地 Codex 历史时，使用不同操作系统用户或受管设备。
4. 仅在客户控制且管理员权限受限的主机运行 Runner。
5. 把成员 Key、上游凭据、日志、备份和诊断信息都视为敏感数据。
6. 按成员审查用量；人员或工作负载退出使用范围时立即撤销 Key。

完整使用模式见[运行多个独立 Codex 客户端](multiple-independent-codex-clients.md)，产品与客户责任见[服务边界](../service-boundaries.md)。
